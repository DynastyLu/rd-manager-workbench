# 员工档案编辑、归档、恢复与永久删除设计

**日期：** 2026-07-30  
**范围：** 员工档案生命周期，不修改员工周报、项目进展和统计口径

## 1. 目标

员工管理必须明确区分四种操作：

1. **编辑**：修改在职员工的姓名、部门、岗位、工作方向、负责人、状态、周容量、发展目标和备注。
2. **归档**：员工不再参与新的工作计划和人员选择，但历史工作数据继续保留。
3. **恢复并编辑**：将已归档员工恢复为可用状态，并立即允许修改档案。
4. **永久删除**：仅删除没有历史业务引用的员工档案；有关联数据时阻止删除并说明原因。

## 2. 产品行为

### 2.1 在职员工

- 员工目录默认只展示未归档员工。
- 每行提供“查看、编辑、归档”操作。
- 编辑使用现有员工档案表单和校验规则。
- 归档必须二次确认，并明确说明历史数据不会被删除。

### 2.2 已归档员工

- 员工目录增加“在职员工 / 已归档”切换。
- 已归档列表只展示归档员工，不参与部门、项目、周报和任务的新建选择。
- 每行提供：
  - 查看历史档案；
  - 恢复并编辑；
  - 永久删除。
- “恢复并编辑”先恢复原记录，再打开编辑表单，保留原员工 ID 和全部历史关联。

### 2.3 新建同名员工

- 新建时如果存在同名的在职员工，继续返回“员工姓名已存在”。
- 新建时如果只存在同名的已归档员工，返回可识别的“员工已归档”冲突，并携带可恢复员工的 ID 与姓名。
- 前端展示“该员工档案已归档”，提供“恢复并编辑”和“取消”。
- 不自动创建第二条同名记录，避免历史数据被拆成两个人。

### 2.4 永久删除

- 永久删除前必须输入或确认员工姓名，并经过二次确认。
- 后端在同一事务内锁定员工记录并检查以下历史引用：
  - 员工工作项；
  - 下周计划；
  - 已解析的导入行；
  - 资源负荷。
- 存在任一历史引用时返回 `EMPLOYEE_DELETE_BLOCKED`，响应只包含各类引用数量和用户可理解的说明，不返回数据库内部信息。
- 没有历史引用时，在事务内删除员工技能等从属档案，再永久删除员工记录。
- 在职员工不能直接永久删除，必须先归档，防止误操作。
- 员工活动时间线与审计记录不作为永久删除阻塞项；永久删除后通过 `employeeId = null` 保留审计证据。
- 永久删除写入审计日志；归档、恢复和编辑也写入对应活动记录。

## 3. 后端接口

### 3.1 列表

`GET /api/employees?archiveState=ACTIVE|ARCHIVED`

- 默认 `ACTIVE`，兼容现有调用。
- `ARCHIVED` 只返回已归档员工。
- 搜索、部门和工作方向筛选对两个状态一致生效。

### 3.2 恢复

`POST /api/employees/:id/restore`

- 只恢复已归档员工。
- 重复恢复返回当前员工，不重复写入副作用。
- 若姓名与另一条在职档案冲突，返回明确冲突。

### 3.3 永久删除

`DELETE /api/employees/:id/permanent`

- 只接受已归档员工。
- 无历史引用时返回 `204`。
- 有历史引用时返回 `409 EMPLOYEE_DELETE_BLOCKED` 和分类计数。

### 3.4 新建冲突

当名称命中已归档员工时，`POST /api/employees` 返回：

```json
{
  "code": "EMPLOYEE_ARCHIVED_EXISTS",
  "message": "Employee is archived",
  "details": {
    "employeeId": "employee-id",
    "displayName": "员工姓名"
  }
}
```

## 4. 前端结构

- 员工目录页增加档案状态页签或分段控件，状态写入 URL，刷新后保持。
- 复用现有 `EmployeeProfileForm`，不创建第二套编辑表单。
- 新增归档员工查询、恢复 mutation 和永久删除 mutation。
- 永久删除弹窗展示引用检查结果；被阻止时保留员工记录并允许恢复。
- 所有成功操作统一失效员工目录、员工详情、团队进展、资源负荷和全局搜索缓存。
- 加载、空状态、接口失败和重复点击均有明确反馈。

## 5. 数据与兼容性

- 保留 `ResourceProfile.displayName` 全局唯一约束，防止同一员工产生两套历史。
- 不修改现有员工 ID，不迁移或复制历史记录。
- 不把归档解释为删除；归档记录可恢复，永久删除记录不可恢复。
- 现有 `DELETE /api/employees/:id` 继续表示归档，避免破坏已有调用。

## 6. 测试与验收

### 后端

- 新建同名在职员工返回普通重名冲突。
- 新建同名已归档员工返回可恢复冲突和员工 ID。
- 恢复后员工重新出现在默认列表，历史关联保持不变。
- 有历史引用时永久删除被阻止并返回分类计数。
- 无历史引用的已归档员工可以永久删除。
- 在职员工不能直接永久删除。

### 前端

- 在职员工可编辑和归档。
- 已归档列表可查询、搜索、恢复并编辑。
- 新建同名已归档员工时出现恢复入口。
- 永久删除成功后从已归档列表消失。
- 删除被阻止时展示具体原因，不错误移除列表项。

### 浏览器验收

1. 新建员工并编辑部门。
2. 归档后从在职列表消失、出现在已归档列表。
3. 再次新建同名员工，选择恢复并编辑。
4. 对无历史数据员工完成永久删除。
5. 对已有周报历史员工尝试永久删除，确认被安全阻止且历史报表仍可读取。
