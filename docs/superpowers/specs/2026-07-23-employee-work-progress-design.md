# 员工工作计划、总结与进展看板设计

日期：2026-07-23  
状态：用户已确认，可进入实施

## 1. 背景与目标

研发主管需要在本地工作台内统一管理员工档案，并上传员工填写的周工作计划与总结。系统应在保证原始数据可追溯的前提下，自动形成团队、员工和项目三个维度的周/月工作进展看板。

本功能不得形成一套与项目管理、资源负荷和风险管理割裂的数据。员工填报中的项目、任务、工时和风险应与现有对象双向关联，主管应能从员工进展下钻到项目，也能从项目详情查看参与员工的工作贡献。

首版继续遵循本地单人管理员模式，不引入员工账号、多人协作或审批流。

## 2. 成功标准

- 管理员可以维护员工档案并下载统一 Excel 模板。
- 管理员可以上传一份包含全体员工的周计划与总结文件。
- 正式写入前可预检员工、项目、任务、日期、完成度和工时等数据。
- 员工按姓名唯一匹配，项目按项目编号精确匹配，系统不做不可解释的模糊猜测。
- 错误行和未解决关联会阻断提交，并可下载错误行文件修正。
- 成功提交后立即生成团队、员工和项目范围的周进展快照，同时刷新受影响月份的月进展快照。
- 团队总览可下钻到员工详情、原始工作项、项目和任务。
- 项目详情可反向查看本周期参与员工、投入工时、完成事项、下期计划和风险。
- 同周期重复上传采用显式版本替换，旧版本可追溯和恢复。
- 导入、修订、关联、提交、失败和恢复操作均写入审计日志。

## 3. 已确认的产品决策

### 3.1 上传方式

- 使用系统提供的统一 `.xlsx` 模板。
- 每个周期上传一份包含所有员工的汇总文件。
- 首版主要支持自然周计划与总结；月看板由有效周数据自动聚合。
- 文件中的一项工作占一行，不使用“每位员工一行、多个事项写成长文本”的结构。

### 3.2 唯一匹配规则

- 员工以姓名唯一匹配。
- 首版员工姓名在全库范围内唯一，包括已归档档案；离职后重新入职继续启用原档案。
- 姓名不存在时，该行进入待处理状态，禁止提交。
- 项目通过项目编号精确匹配。
- 任务编号可选；填写任务编号时，任务必须属于填写的项目。
- 项目名称只用于展示和人工核对，不参与自动关联。

### 3.3 重复上传规则

每份文件代表一个周期的完整团队数据。同一周期再次上传时创建新版本：

1. 新文件先创建暂存导入批次。
2. 管理员完成预检、关联补充和确认。
3. 新版本成功提交后成为该周期当前有效版本。
4. 旧版本不删除，继续保留用于审计、对比和恢复。
5. 周/月看板只聚合每个周期的当前有效版本。

不使用标题相似度进行逐行覆盖，避免员工修改标题后形成不可预测的重复记录。

## 4. 信息架构与导航

主导航新增一级入口“员工”，路由为 `/employees`。

员工模块包含四个主页签：

1. **团队总览**：团队周/月指标、员工进展、项目贡献和风险提示。
2. **员工档案**：员工列表、基础资料、状态、技能和周容量。
3. **工作明细**：跨员工查看所有已确认工作项，统一筛选和导出。
4. **导入记录**：查看上传批次、状态、错误、版本、原文件和审计信息。

员工详情路由为 `/employees/:employeeId`，包含：

- 工作进展
- 项目贡献
- 负荷与技能
- 导入历史

项目详情增加“团队进展”区域；如果现有页签数量不宜继续增加，则放在“进展”页签内作为独立区块。

## 5. 员工档案

现有 `ResourceProfile` 是本地主管维护的资源档案，应作为员工主数据继续复用，避免重复建立“员工”和“资源”两套人员。

需要扩展的字段：

- `displayName`：姓名，必填且全库唯一。
- `department`：部门。
- `roleTitle`：岗位。
- `managerName`：直属负责人姓名，首版为展示文本，不建立组织树外键。
- `employmentStatus`：`ACTIVE`、`ON_LEAVE`、`LEFT`。
- `weeklyCapacityHours`：周容量，复用现有字段。
- `developmentGoal`：发展目标，复用现有字段。
- `notes`：备注，复用现有字段。
- `archivedAt`：归档时间，复用现有字段。

技能继续复用 `ResourceSkill`。归档员工前，系统提示其未结束项目、未完成任务和未来负荷，但首版只阻断存在未归档负荷条目的情形，保持与现有资源归档规则一致。

前端和 API 对外统一使用“员工”措辞；数据库表可以继续映射现有 `resource_profiles`，以降低迁移风险。

### 5.1 任务编号

现有 `WorkTask` 没有可供员工填写的稳定业务编号。为了支持 Excel 精确关联，增加全局唯一且不可变的 `code`：

- 现有任务在迁移时生成稳定编号。
- 新任务创建时由后端生成编号。
- 任务编号在项目详情、任务列表和导出文件中展示。
- 员工不能通过修改任务标题改变关联结果。

## 6. Excel 模板

### 6.1 模板元信息

模板顶部或专用工作表记录：

- 数据类型：周计划与总结。
- 周期开始日期。
- 周期结束日期。
- 模板版本。

周期开始日期必须为周一，结束日期必须为对应周日。系统以本地时区解析日期，再以稳定日期值保存，不把无时区日期隐式转换成前一天或后一天。

### 6.2 工作明细列

| 列名 | 必填 | 说明 |
| --- | --- | --- |
| 员工姓名 | 是 | 与有效员工档案精确匹配 |
| 工作内容 | 是 | 一项工作一行 |
| 本期计划 | 否 | 本周期计划目标 |
| 本期完成情况 | 否 | 已完成内容和结果 |
| 完成度 | 否 | 0–100 的整数或百分比 |
| 工作状态 | 是 | 未开始、进行中、已完成、有风险、已阻塞 |
| 下期计划 | 否 | 下一周期计划 |
| 风险与阻塞 | 否 | 当前问题、依赖和影响 |
| 计划工时 | 否 | 非负数，最多两位小数 |
| 实际工时 | 否 | 非负数，最多两位小数 |
| 项目编号 | 否 | 精确关联现有项目 |
| 任务编号 | 否 | 精确关联现有任务，且必须属于项目 |
| 备注 | 否 | 其他补充信息 |

如果项目编号和任务编号都为空，该项归入“未关联工作”。管理员可以在预检阶段补充项目或保留未关联状态。

## 7. 导入流程

导入采用五步向导：

1. **选择文件**：只接受系统支持的 `.xlsx` 文件，检查大小、文件名和内容类型。
2. **识别模板**：读取模板版本、周期、工作表和列头。
3. **数据预检**：解析所有行并执行完整业务校验。
4. **补充关联**：集中解决未知员工、未知项目、未知任务和项目任务不一致问题。
5. **确认导入**：展示影响范围和版本替换提示，管理员确认后原子提交。

预检页面必须展示：

- 总行数。
- 校验通过行数。
- 错误行数。
- 待补关联行数。
- 具体行号、字段、原值和错误原因。
- 可下载的错误行 Excel。

正式提交前，服务器必须重新验证：

- 导入批次仍处于可提交状态。
- 预检指纹与当前映射、文件和补充关联一致。
- 员工、项目和任务在提交时仍有效。
- 同周期版本没有被其他提交改变。

## 8. 数据模型

### 8.1 `ResourceProfile` 扩展

继续作为员工主档案，增加 `department`、`managerName` 和 `employmentStatus`。

### 8.2 `EmployeeWorkImportBatch`

保存一次上传、预检和提交的完整生命周期。

字段：

- `id`
- `periodType`：首版固定为 `WEEK`
- `periodStartAt`
- `periodEndAt`
- `version`
- `status`：`UPLOADED`、`PREVIEWED`、`RESOLVING`、`READY`、`IMPORTING`、`COMPLETED`、`FAILED`、`SUPERSEDED`、`EXPIRED`
- `originalName`
- `fileHash`
- `sourceStorageKey`
- `errorStorageKey`
- `templateVersion`
- `previewFingerprint`
- `snapshotStatus`：`NOT_STARTED`、`GENERATING`、`READY`、`FAILED`
- `snapshotError`
- `totalRows`
- `validRows`
- `errorRows`
- `unresolvedRows`
- `importedRows`
- `supersedesBatchId`
- `restoredFromBatchId`
- `committedAt`
- `archivedAt`
- `createdAt`
- `updatedAt`

约束：

- `(periodType, periodStartAt, version)` 唯一。
- 相同文件哈希和相同周期的未过期批次不重复创建。
- 每个周期同一时刻只有一个当前有效的已完成批次。

### 8.3 `EmployeeWorkImportRow`

保存预检阶段的暂存行和错误，避免直接向正式表写入半成品。

字段：

- `id`
- `batchId`
- `rowNumber`
- `rawValues`
- `normalizedValues`
- `status`：`VALID`、`ERROR`、`UNRESOLVED`
- `errors`
- `resolvedEmployeeId`
- `resolvedProjectId`
- `resolvedTaskId`
- `createdAt`
- `updatedAt`

### 8.4 `EmployeeWorkItem`

保存已经确认的员工周期工作事实。

字段：

- `id`
- `employeeId`
- `importBatchId`
- `sourceRowId`
- `periodStartAt`
- `periodEndAt`
- `title`
- `planText`
- `summaryText`
- `completionRate`
- `status`
- `nextPlanText`
- `riskText`
- `plannedHours`
- `actualHours`
- `projectId`
- `taskId`
- `note`
- `rawRow`
- `archivedAt`
- `createdAt`
- `updatedAt`

已确认工作项默认只读。人工更正必须产生可审计修订，或通过新周期版本替换，不直接覆盖原始来源内容。

### 8.5 `EmployeeProgressSnapshot`

保存生成时的指标和来源版本，保证历史看板不会因后续数据变化而悄然改变。

字段：

- `id`
- `scopeType`：`TEAM`、`EMPLOYEE`、`PROJECT`
- `scopeId`：团队为空，员工或项目为对应 ID
- `periodType`：`WEEK`、`MONTH`
- `periodStartAt`
- `periodEndAt`
- `version`
- `metrics`
- `highlights`
- `risks`
- `sourceBatchIds`
- `generatedAt`
- `archivedAt`
- `createdAt`

### 8.6 `ResourceLoadEntry` 扩展

增加两个可选来源字段：

- `employeeWorkItemId`
- `employeeWorkImportBatchId`

来源工作项在有效负荷条目中唯一，防止提交重试产生重复工时。人工登记的既有负荷条目保持两个来源字段为空。

## 9. 提交与自动聚合

确认导入使用数据库事务：

1. 锁定批次和该周期当前有效版本。
2. 重新验证所有暂存行与关联对象。
3. 创建正式 `EmployeeWorkItem`。
4. 将计划工时同步为现有 `ResourceLoadEntry`，并记录来源批次和来源工作项。
5. 将上一有效批次标记为 `SUPERSEDED`。
6. 将新批次标记为 `COMPLETED`。
7. 记录审计事件。

事务成功后执行可重试的派生处理：

- 生成团队周快照。
- 为所有受影响员工生成员工周快照。
- 为所有受影响项目生成项目周快照。
- 按本周结束日期所在月份刷新团队、员工和项目月快照。
- 失效员工、项目、报表和搜索相关缓存。
- 刷新全局搜索索引。

快照在工作项事务提交后同步生成。生成期间 `snapshotStatus` 为 `GENERATING`，成功后为 `READY`。如果快照生成失败，正式工作项不回滚，批次保持 `COMPLETED`，同时将 `snapshotStatus` 标记为 `FAILED` 并记录 `snapshotError`。提交接口返回成功但带有明确警告，页面允许管理员调用重建接口；重建操作必须幂等。

## 10. 指标口径

### 10.1 周期归属

- 周快照使用模板中的周一至周日。
- 月快照按周结束日期归属月份。
- 月快照只使用每周当前有效批次。
- 缺少某周数据时不补零，必须展示“数据不完整”和缺失周期。

### 10.2 团队和员工指标

- 计划工作项：当前有效工作项数量。
- 已完成：状态为 `COMPLETED` 的工作项数量。
- 按期完成率：已完成数量除以存在明确状态的工作项数量。
- 平均完成度：只统计填写了完成度的工作项。
- 计划工时：计划工时求和。
- 实际工时：实际工时求和。
- 风险与阻塞：状态为有风险或已阻塞，或风险文本非空的工作项数量。
- 项目覆盖：存在项目关联的不同项目数量。
- 未关联工作：没有项目和任务关联的工作项数量。

指标分母为零时返回 `null`，前端显示“暂无数据”，不得显示误导性的 `0%`。

### 10.3 项目贡献

项目维度聚合：

- 参与员工数。
- 工作项总数和已完成数。
- 平均完成度。
- 计划/实际工时。
- 员工完成事项。
- 员工下期计划。
- 风险与阻塞。

一个工作项最多关联一个项目和一个属于该项目的任务。

## 11. 项目、负荷和风险联动

### 11.1 项目与任务

- 员工工作项保存 `projectId` 和可选 `taskId`。
- 员工详情点击项目或任务进入现有项目空间。
- 项目详情的团队进展点击员工，返回同一周期的员工详情。
- 项目归档后历史工作项仍保留项目快照信息，但新导入不得关联已归档项目。

### 11.2 资源负荷

- 有计划工时的工作项同步到现有 `ResourceLoadEntry`。
- 关联任务时负荷类型为 `TASK`；只关联项目时为 `PROJECT`；无项目时为 `OTHER`。
- 负荷条目记录来源工作项和导入批次，以支持版本替换和回滚。
- 同周期新版本生效时，旧版本产生的负荷条目同时归档，新版本条目成为有效数据。

### 11.3 风险

- 风险文本和风险状态首先保留在员工工作项。
- 管理员可将某条工作风险转换为现有项目风险。
- 转换后保存双方 ID，避免重复转换，并支持从风险返回员工原始上报。
- 未关联项目的工作风险不能直接转为项目风险，需先选择项目。

### 12.1 团队总览

包含：

- 周/月切换和周期选择。
- 部门、项目、状态筛选。
- 计划工作项、完成率、项目覆盖、风险等指标卡。
- 员工进展表。
- 项目贡献排行。
- 风险与阻塞区域。

### 12.2 员工详情

展示：

- 本周期指标。

### 12.4 导入记录

展示：

- 文件名和文件哈希。

## 14. 错误处理与恢复

- 文件格式、大小或模板版本不支持：拒绝上传并给出明确原因。
- 模板缺少必填列：停止预检。
- 日期、完成度、状态或工时非法：标记具体行和字段。
- 员工不存在或姓名重复：进入待处理，管理员可以选择已有员工或新建员工后重新校验。
- 项目编号不存在：进入待处理，管理员选择项目或保留未关联。
- 任务不存在或不属于项目：进入待处理。
- 同一文件重复上传：返回已有批次并提示，不重复存储。
- 正式提交失败：事务回滚，批次进入 `FAILED`，允许安全重试。
- 快照生成失败：保留已提交事实数据，进入“待重建快照”状态。
- 恢复旧版本：系统从目标旧批次复制已确认行，创建一个新的周期版本，并通过正常提交链路使其成为当前有效版本；新批次记录 `restoredFromBatchId`。任何已有版本都不物理删除。

## 15. 审计、文件与本地安全

- 原 Excel、错误文件和导出文件使用现有本地存储端口。
- 文件名必须净化，存储键由系统生成，不接受用户路径。
- 记录上传、预检、补关联、提交、版本替换、恢复、风险转换和快照重建事件。
- 审计记录包含操作者、本地时间、对象、前后状态和必要的业务摘要。
- 原始行保存在受控 JSON 字段中，不直接渲染为 HTML。
- 首版本地单人使用，操作者使用系统本地管理员身份。
